## 结论先行

在繁体中文（台湾地区）Windows 环境下编写 VBA，VBE 编辑器有以下硬性事实：

1. **VBE 只接受繁体中文**。代码窗口、字符串常量、注释遵循系统 ANSI 代码页 **CP950（Big5）**，不是 UTF-8，也没有任何配置项能改成 UTF-8 源码模式。
2. **简体中文会乱码**。简体字中不在 Big5 字符集内的字（GBK 特有字），粘贴进 VBE 后直接显示为 `?` 或乱码。
3. **繁体注释直接复制粘贴进 VBE，也会乱码**。因为复制来源的文件如果没有被按 CP950 正确解码，剪贴板里拿到的就是乱码字符，粘贴自然还是乱码。
4. **正确做法**：新建一个 txt 文档，用 **Word / 记事本 / VS Code 选择 CP950 编码**，或用 **Notepad++ / Notepad3 按编码打开**，先把内容粘贴进这个文档（让字节被正确解码成 Unicode），**再复制，然后粘贴进 VBE**，才正常。

一句话：**不是「繁体字」本身的问题，而是「来源文件的字节有没有被按 CP950 正确解码」的问题。**

## 为什么会这样：编码原理

### 文本的两种形态：内存里的 Unicode 与文件里的字节

任何文本在程序内存里都是 **Unicode 字符**，但**保存到文件时必须按某种编码（代码页）转换成字节**。打开文件时再按某种编码把字节还原成字符。

关键点是：**文件本身不记录自己是什么编码**（除非带 BOM）。同一个字节串，用什么编码去解，结果完全不同：

![编码原理]( /downloads/2026-10-28-vba-big5-vbe-encoding-编码原理图.png)

上图是本机的真实演示：一份繁体文本按 **CP950** 编码保存为文件后：

- 繁体系统（ANSI 代码页 = CP950）打开 → **正常显示**
- 简体系统（ANSI 代码页 = GBK/936）打开 → **乱码**（`砼珍□□代刚爹秆`）

下面的截图是同一份 CP950 文件在简体系统记事本里的真实效果——GBK 去解 Big5 字节，注释行全部乱码：

![记事本用 GBK 打开 CP950 文件乱码]( /downloads/2026-10-28-vba-big5-vbe-encoding-记事本gbk打开cp950乱码.png)

把方向反过来，就是繁体系统里的场景：**简体系统写出的 GBK 字节，拿到繁体系统被 Big5 解码 → 乱码**。原理完全相同，只是方向相反。

### VBE 的原生限制

VBE 是 1990 年代的架构，代码窗口、字符串、注释全部遵循**系统 ANSI 代码页**：

- 繁体系统 → CP950（Big5）
- 简体系统 → GBK（936）

VBE **没有**「另存为 UTF-8」之类的选项，也**不接受 UTF-8 源码直接粘贴**（UTF-8 字节流会被按 ANSI 逐字节解码，产生大量乱码字符）。所以代码层面无法绕过——要么用系统代码页内能表示的字符（繁体），要么别把文本硬编码在代码里（放到工作表单元格，单元格是 Unicode，不受代码页约束）。

## 各种软件、各种状态的编码形态

用本机实测，看看不同编辑器对同一份 CP950 文件的处理差异：

### 记事本（Notepad）

无 BOM 的文件按系统 ANSI 代码页解码。简体系统上打开 CP950 文件 → 乱码（见上图）；繁体系统上打开 GBK 简体文件 → 同样乱码。记事本本身没有「指定编码打开」的选项，只有保存时可选编码。

### VS Code

VS Code 默认按系统语言猜测编码，简体系统上把 CP950 文件按 GBK 打开，注释行变成乱码方块：

![VS Code 默认按 GBK 打开，乱码方块]( /downloads/2026-10-28-vba-big5-vbe-encoding-vscode默认gbk打开乱码方块.png)

解决办法：命令面板（Ctrl+Shift+P）→「通过编码重新打开」→ 选 **Traditional Chinese (Big5 / CP950)**：

![VS Code 通过编码重新打开]( /downloads/2026-10-28-vba-big5-vbe-encoding-vscode通过编码重新打开.png)

选 CP950 后，繁体注释全部正常显示：

![VS Code 选 CP950 后繁体正常]( /downloads/2026-10-28-vba-big5-vbe-encoding-vscode选cp950后繁体正常.png)

VS Code 的编码选择器里能看到「Traditional Chinese (Big5)」，对应代码页 950——这就是我们要选的编码。

### Notepad++ / Notepad3

Notepad++ 的编码自动检测能力强，同一份 CP950 文件打开即自动识别为 Big5，正常显示，无需手动设置：

![Notepad++ 自动识别 Big5 正常显示]( /downloads/2026-10-28-vba-big5-vbe-encoding-notepadplusplus自动识别big5正常.png)

如果打开仍是乱码，用菜单「编码 → 字符集 → 中文 → Big5」手动切换即可。Notepad3 同属此类。

### Word

Word 打开文本文件时可指定编码（文件 → 打开 → 选择文件 → 编码），选择繁体中文（Big5）即可正常。这也是结论里推荐的中转工具之一。

### VBE（示意）

VBE 本身没有编码选项，行为如下（图为示意——在自己电脑上是简体环境，无法真实复现繁体 VBE，故用示意图呈现）：

![繁体 VBE 乱码与正确做法示意]( /downloads/2026-10-28-vba-big5-vbe-encoding-VBE乱码示意.png)

- 简体注释直接粘贴 → 全部变 `?`
- 繁体注释从未正确解码的来源复制 → 也乱码
- 经 CP950 正确打开的 txt 中转后再复制粘贴 → 正常

## 剪贴板里到底是什么：复制正常 ≠ 粘贴正常

这是大家困惑最多的地方：**复制的时候，屏幕上明明显示的是正常的繁体，粘贴进 VBE 却变成了乱码**；反过来，**从 VBE 里复制出来的繁体，粘贴到别处也乱码**。要理解这个现象，必须看剪贴板内部到底存了什么。

![剪贴板内部结构]( /downloads/2026-10-28-vba-big5-vbe-encoding-剪贴板编码形态图.png)

**剪贴板里同时存放两份格式副本：**

1. **Unicode 层（`CF_UNICODETEXT`）**：UTF-16LE 字符数据。复制时，来源程序把自己内存里的 Unicode 字符原样放进这一层。**你屏幕上看到的就是这一层**——它正常，说明 Unicode 层正常。
2. **ANSI 字节副本（`CF_TEXT`）**：来源程序额外生成的一份**字节**，按**来源程序所在系统的 ANSI 代码页**编码（繁体系统 = CP950）。这是 Windows 为兼容老程序保留的格式，复制时总会被同时生成。

**粘贴时，目标程序二选一读取：**

- **现代程序（记事本、VS Code、现代网页、聊天工具）读 Unicode 层** → 字符原样进入，正常。
- **老程序 / 部分老控件读 ANSI 副本** → 按**目标系统代码页**解码。

乱码就出在第二种情况：

- 来源是繁体系统 → ANSI 副本是 **CP950 字节**
- 目标是简体系统 → 用 **GBK** 去解 CP950 字节 → **乱码**（`砼珍□□代刚爹秆`）
- 反之亦然：简体来源的 ANSI 副本是 GBK 字节，被繁体系统用 CP950 解 → 乱码

所以「复制正常、粘贴乱码」的完整解释是：

> 你看到的「正常」来自剪贴板的 **Unicode 层**；你粘出来的「乱码」来自剪贴板的 **ANSI 字节副本**，加上目标代码页不匹配。**来源显示正常 ≠ 粘贴结果正常**——结果取决于目标程序读哪一份，以及双方代码页是否一致。

**从 VBE 复制出来也是一样：**

- VBE 复制时同样放两份：Unicode 层（你屏幕看到的正常繁体）+ ANSI 副本（按系统代码页生成，繁体系统就是 CP950 字节）。
- 粘贴到读 Unicode 层的现代程序 → 正常；
- 粘贴到读 ANSI 副本的旧环境（老控件、老式上传/保存通道）→ 繁体系统的 CP950 字节到了简体环境被按 GBK 解 → 乱码。

**还有一个叠加因素**：如果 VBE 代码窗口里本身已经是 `?`（当初粘贴时就已经乱码），那 Unicode 层里存的**就是 `?` 本身**——再怎么复制、贴到哪里都是 `?`，因为字符在进 VBE 的那一刻就已经丢失了。

**安全结论：**

- **现代编辑器之间复制粘贴**（双方都读 Unicode 层）→ 永远正常。
- 乱码只发生在两种情况：① 某一边读了 ANSI 副本且代码页不匹配；② 字符在进入剪贴板之前就已经损坏（如 VBE 里已是 `?`）。
- 中转文件方案之所以可靠，正是因为：**先让字节按 CP950 被正确解码成 Unicode（屏幕正常），再用现代编辑器之间传递（读 Unicode 层），最后粘贴进 VBE 时拿到的就是正确的 Unicode 字符**——绕开了所有 ANSI 副本和代码页匹配的坑。

## 推荐的完整流程

```text
目标：把一段带中文注释的 VBA 代码安全放进繁体系统的 VBE

1. 新建一个 .txt 文件
2. 用以下任一方式打开，并确认编码为 CP950（Big5）：
   - Word：打开时选「繁体中文 (Big5)」编码
   - VS Code：右下角/命令面板 → 通过编码重新打开 → Traditional Chinese (Big5)
   - Notepad++ / Notepad3：编码 → 字符集 → 中文 → Big5（或打开即自动识别）
   - 记事本：本身无编码选择，但保存时可选编码（若文件是 UTF-8 需另存为 ANSI 后重新按编码处理）
3. 把代码粘贴进这个 txt，保存（保持 CP950）
4. 在 txt 里 Ctrl+A 全选、复制
5. 到 VBE 里粘贴 —— 繁体中文正常显示
```

## 附：繁体环境 VBA 代码规范（厂区实践总结）

以下是在厂区繁体版 Office + 中文(台湾)地区设定环境下做 Excel 工具（IE 报表、UPPH、良率、工时、SOP 工具）踩坑后的硬性规范：

1. **代码注释、硬编码字符串，只用繁体文字**。避免 Big5 缺字乱码。
2. **`WorksheetFunction` 固定用英文函数名**（如 `Application.WorksheetFunction.VLookup`）。写本地化中文名（如「垂直尋找」「總和」）会直接报错。
3. **业务逻辑禁止比对 `MonthName` / `WeekdayName` 返回的文字**。繁体环境下它们返回繁体中文，应只用 `Month()` / `Weekday()` 的数字判断。
4. **外部日期字符串不用 `CDate` 直接解析**（跟随系统短日期格式，易错）。用 `Split` + `DateSerial(y, m, d)` 构造日期序列号。
5. **跨环境分发模块，不要依赖 VBE 原生导出 `.bas`**。VBE 导出 `.bas` 用系统 ANSI 代码页（繁体 = CP950），繁体导出给简体 VBE 导入会乱码；改用文件/文本等载体传递代码。
6. **跨环境交付带工程密码的 VBA 工程（xlsm）存在加载/密码校验风险**；旧格式 `.xls` 的二进制工程兼容性更差。交付前建议移除工程密码。
7. **`StrConv` 可做繁简转换**（`StrConv(文字, vbSimplifiedChinese)` / `StrConv(文字, vbTraditionalChinese)`），但只转换字符串内容，**救不了源码里已经乱码的硬编码**。
8. **VBE 语法关键字永远是英文**（`If` / `For` / `Dim` / `Function` 等），不受 Office 界面语言影响，不存在中文关键字版本。
9. **业务文本不要硬编码在代码字符串里**，放到工作表单元格读取——单元格是 Unicode，不受 CP950 约束。

## 小结

- 繁体系统 VBE 的编码基线是 **CP950（Big5）**，这是根源。
- 乱码 = 字节与代码页不匹配，**剪贴板本身不背锅**。
- 正确姿势：**txt + CP950 编码打开 → 复制 → 粘贴进 VBE**。
- 长期看：注释/字符串统一繁体、文本放单元格、跨环境用文件而非 `.bas` 传递，能从根上避开大部分编码坑。
